# Spring Boot 综合项目复盘

> 复盘主题：订单、库存、事务和审计日志
>
> 当前阶段：已完成订单创建、订单取消、重复取消、异常回滚、异常恢复和库存不足等核心功能验证。

## 一、客观评价

这份复盘已经能够从业务角度解释主要设计，而不是只描述接口返回结果。当前理解比较扎实的部分包括：

- 能意识到请求对象和数据库对象属于不同边界，不能因为字段看起来相似就直接复用；
- 能识别前端金额不可信，知道价格和总额必须由服务端根据数据库数据计算；
- 能意识到库存操作存在并发问题，而不是只按单线程顺序理解代码；
- 能把事务和订单、库存、明细、日志的一致性联系起来；
- 能把 `operation_logs` 识别为业务审计记录，而不是普通调试输出；
- 已通过真实请求和 Navicat 结果验证正常提交、回滚、取消和库存不足路径。

目前还需要加强的地方：

- “请求成功”与“业务成功”要区分。当前项目约定业务异常使用 HTTP `200`，由响应体 `code` 表示业务失败，这是一种接口协议选择，不是 HTTP 唯一标准；
- 事务触发条件需要从“Bean 调用”精确到“外部调用 Spring 创建的代理对象”；
- 库存失败不能只说“其他操作会影响”，要能说明先查后改的竞态窗口、条件更新和受影响行数；
- 审计日志的回滚语义要结合业务目的说明：创建订单失败时，创建日志也应回滚，否则会出现没有对应订单的审计记录；
- 当前代码仍是学习型实现，尚未证明幂等、并发压力、复杂状态机、生产级日志治理和数据库性能能力。

## 二、问题修正与机制说明

### 1. 为什么 `CreateOrderRequest` 不能直接作为数据库插入对象？

你的理解方向正确，但原因不只是“数据库分表”。`CreateOrderRequest` 是 HTTP API 的输入模型，表达“客户端想创建什么”；数据库对象表达“某张表的一行数据”；两者的职责、生命周期和可信程度都不同。

一次创建订单请求可能包含：

```text
CreateOrderRequest
  buyerId
  items[]
    productId
    quantity
```

而数据库至少拆成：

```text
orders          订单主表
order_items     订单明细表
inventories     库存表
operation_logs  操作日志表
```

因此 Service 必须完成一次业务组装：

```text
请求 DTO
  -> 查询商品和库存
  -> 计算金额、校验业务规则
  -> 组装 Order
  -> 组装多个 OrderItem
  -> 组合多个 Mapper 完成事务
```

请求中不应信任或允许客户端设置这些服务端字段：

- `orderId`；
- `unitPrice`；
- `totalAmount`；
- `createdAt`；
- `status`；
- `version`。

当前练习直接把 `model.OrderItem` 放在请求 DTO 中可以帮助理解嵌套校验，但更清晰的长期结构是：

```text
CreateOrderRequest
CreateOrderItemRequest
Order
OrderItem
```

前两个属于 API 模型，后两个属于领域或持久化模型。

### 2. 为什么订单总额必须由后端根据数据库价格计算？

你的理解正确。前端传来的价格可能被修改，或者客户端使用了过期价格。后端应该只接受商品 ID 和购买数量，然后从数据库读取当前有效价格：

```text
商品单价 = 数据库中的 products.price
单项金额 = 商品单价 * quantity
订单总额 = 所有单项金额之和
```

金额使用 `BigDecimal`，不能使用 `double` 进行结算。订单明细还应保存成交时的 `unit_price` 快照，因为商品表价格未来可能改变，历史订单不能跟着变化。

这也是为什么不能直接信任请求中的 `unitPrice` 或 `totalAmount`：它们属于客户端输入，而价格规则属于服务端业务规则。

### 3. 为什么扣库存不能只依赖 Java 层的“先查询再更新”？

你的理解方向正确，但需要具体说明竞态条件。

如果只这样做：

```text
1. SELECT available_quantity
2. Java 判断库存足够
3. UPDATE available_quantity
```

两个请求可能同时读取到相同库存：

```text
库存初始为 10
请求 A 读到 10
请求 B 读到 10
请求 A 扣减 8
请求 B 也根据旧数据扣减 8
```

Java 的判断无法保护这段时间窗口。当前项目使用数据库条件更新：

```sql
UPDATE inventories
SET available_quantity = available_quantity - #{quantity},
    version = version + 1
WHERE product_id = #{productId}
  AND available_quantity >= #{quantity}
  AND version = #{version}
```

这里的三个条件分别表示：

- `product_id`：找到具体商品；
- `available_quantity >= quantity`：数据库层面保证扣减后不会小于零；
- `version = version`：确认读取到的仍是当前版本，避免使用旧数据覆盖并发修改。

Service 必须检查更新条数：

```java
if (affectedRows == 0) {
    throw new InsufficientStockException("库存不足或库存已发生变化");
}
```

更新条数为 `0` 时，可能是库存不足，也可能是版本冲突。当前阶段可以统一当作业务失败处理；生产系统可能进一步区分并重试。

### 4. 如果日志插入失败，哪些数据必须回滚？

不能只说“库存和订单回滚”。在创建订单的同一个事务中，以下写操作都应该回滚：

```text
库存扣减
orders 主表插入
order_items 明细插入
operation_logs 创建日志插入
```

原因是这些记录共同描述一个业务事实。如果订单主表和库存已经提交，但日志插入失败，就会出现库存已经减少、订单数据不完整、操作记录缺失的状态，后续无法可靠审计和排查。

当前项目中，`@Transactional` 放在 Service 方法上，多个 Mapper 使用同一个 Spring 管理的事务连接。方法正常结束时统一提交；运行时异常向外抛出时统一回滚。

取消订单同理，以下操作应处于同一事务：

```text
恢复库存
修改订单状态
写入取消日志
```

如果恢复库存成功但状态更新失败，库存也必须回滚，不能留下“订单仍是 CREATED、库存却已经恢复”的中间状态。

### 5. `@Transactional` 由哪个代理边界触发？同类内部调用有什么影响？

“通过 Bean 调用时触发”表述不够准确。更准确的说法是：

> 外部对象通过 Spring 容器创建的代理对象调用带有 `@Transactional` 的方法时，事务拦截器才有机会介入。

调用链可以简化为：

```text
Controller
  -> Spring 代理对象
      -> 事务拦截器开启事务
          -> 真实 OrderService 方法
          -> 正常结束则提交，异常则回滚
```

如果在同一个类中这样调用：

```java
this.otherMethod();
```

这是目标对象内部的普通 Java 调用，不会再次经过代理，因此 `otherMethod()` 上的事务注解不会单独触发新的代理拦截。

还要注意：

- Spring 默认对运行时异常和 `Error` 回滚；
- 受检异常是否回滚要根据 `rollbackFor` 等配置确认；
- 事务边界通常放在 Service 的业务方法，而不是 Controller 或 Mapper；
- 不要在 Spring 管理的 MyBatis 事务中手动 `openSession()`、`commit()` 或 `rollback()`。

### 6. `operation_logs` 是业务审计记录还是调试日志？

当前设计属于业务审计记录。它描述的是业务动作，例如：

```text
订单 9 创建
订单 9 取消
```

审计记录与调试日志的区别：

| 类型 | 目的 | 生命周期 | 内容要求 |
| --- | --- | --- | --- |
| 业务审计记录 | 追踪谁对哪个业务对象做了什么 | 通常需要长期保留 | 稳定、可查询、不可随意修改 |
| 调试日志 | 排查程序运行过程 | 可按级别和保留策略清理 | 便于定位问题，允许较详细 |

调试日志可以通过日志级别和保留策略清理，但审计记录通常受到业务、合规或运营要求约束。审计表也不是绝对不能删除，而是不能像临时 `System.out.println` 一样随意丢弃；是否归档、保留多久由业务规则决定。

当前项目把操作日志放进订单事务中，因此订单创建失败时日志也会回滚。这保证了审计记录不会指向一个最终不存在的订单。

### 7. 如果未来改成异步消息扣库存，当前事务边界会发生什么变化？

当前实现是同步本地事务：

```text
同一个 HTTP 请求
  -> 同一个 Service 方法
  -> 同一个数据库事务
  -> 订单、明细、库存、日志一起提交或回滚
```

如果改为异步消息：

```text
请求线程创建订单
  -> 发送“扣库存”消息
  -> 消费者稍后扣库存
```

订单数据库事务和消息消费者的库存事务通常不再属于同一个本地事务，因此可能出现：

- 订单已创建，但消息发送失败；
- 消息重复投递，库存被重复扣减；
- 订单创建成功，但库存处理暂时未完成；
- 消费者失败后需要重试或补偿。

这时需要重新设计一致性方案，例如：

- 使用事务消息或可靠消息投递；
- 使用 Outbox 表，把业务事件和订单写入同一数据库事务，再由后台投递；
- 消费者根据业务键或消息 ID 做幂等处理；
- 对失败消息进行重试、死信和人工补偿；
- 用订单状态表示“待扣库存”“库存已确认”“库存失败”等中间状态。

所以异步化不是简单地把方法改成线程或消息调用，而是改变了事务边界和最终一致性模型。当前综合项目先使用同步本地事务是合理的，重点是先掌握原子性和业务边界。

## 三、结合当前代码的补充问题

下面问题不影响当前核心功能验收，但属于后续改进边界：

### 1. DTO 与 Model 仍有复用

当前 `CreateOrderRequest.items` 使用了 `model.OrderItem`。练习阶段可以接受，但它让 `id`、`orderId`、`unitPrice` 等服务端字段暴露在请求模型中。后续可拆为 `CreateOrderItemRequest` 和 `OrderItem`。

### 2. 基本类型字段无法表达“未传入”

如果 `quantity` 使用 `int`，默认值是 `0`，`@NotNull` 对基本类型没有实际作用。更清晰的写法是：

```java
@NotNull(message = "数量不能为空")
@Min(value = 1, message = "数量必须大于 0")
private Integer quantity;
```

当前项目可以通过 `@Min` 拦截 `0`，但“未传”和“传了 0”仍然无法区分。

### 3. 商品和库存不存在时应显式抛出业务异常

Service 当前先调用 `product.getEnabled()` 或 `inventory.getAvailableQuantity()`。如果数据库没有对应记录，可能先出现 `NullPointerException`，最终被当作 `500`。更清晰的业务行为是显式返回“商品不存在”或“库存记录不存在”。

### 4. 状态更新还可以增加状态条件

取消订单时先查询状态再更新，能够完成当前单线程练习。但在并发请求下，两个请求都可能先读到 `CREATED`。更严格的更新可以把原状态放入 SQL 条件，并检查更新条数，例如只允许 `CREATED -> CANCELLED`。

### 5. 业务响应码和 HTTP 状态码是两个层次

当前项目约定业务异常返回 HTTP `200`，再由响应体中的 `code` 表示失败；校验错误和系统异常仍可使用 HTTP `400`、`500`。这种方案可以使用，但必须写成统一的前后端协议，不能让不同接口随意混用。
