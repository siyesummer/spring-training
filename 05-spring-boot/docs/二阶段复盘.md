# Spring Boot 第二轮复盘

## 一、客观评价

你已经能够从依赖树和运行日志反推框架行为，而不是只记住“加一个 Starter 就能用”。本轮复盘中对 `MybatisAutoConfiguration`、`@MapperScan`、`namespace`、`#{}`、`resultMap` 和 `useGeneratedKeys` 的方向判断基本正确；结合 Apifox、Navicat 和 MyBatis SQL 日志，你也验证了 CRUD、动态 SQL、批量评论、一对多映射和 Spring 事务。

当前需要提升的主要是职责边界和表达精度：

- Starter、自动配置类、Mapper 注册器和具体 Bean 不是同一个层次；
- `SqlSessionTemplate` 不是简单的“事务开关”，事务真正由 Spring 事务拦截器和事务管理器控制；
- `<collection>` 不是简单“按左表 id 分级”，而是按父子结果映射规则合并 JOIN 的多行结果；
- Repository 适配层目前只隔离了任务 CRUD，评论和详情仍由 Service 直接注入 Mapper；
- MyBatis 自动配置的是基础设施，SQL、参数、结果映射和业务规则仍由项目自己负责。

综合判断：你已经达到“能够独立使用并解释 Spring Boot + MyBatis 基础链路”的阶段，具备进入下一阶段或整理阶段文档的基础；这不等同于已经掌握复杂 SQL 调优、多数据源和生产级数据访问架构。

## 二、问题修正与机制说明

### 1. `mybatis-spring-boot-starter`、`mybatis-spring` 和 MyBatis 核心框架的关系

原来的“Starter 包含了 MyBatis 功能需要的 Jar 包”方向正确，但可以分成三层：

```text
mybatis-spring-boot-starter
  -> 依赖组合入口
  -> 引入 mybatis-spring-boot-autoconfigure
  -> 引入 mybatis-spring
  -> 引入 mybatis 核心框架
```

- `mybatis`：负责 SQL 映射、`SqlSessionFactory`、执行器、参数绑定和结果映射。
- `mybatis-spring`：把 MyBatis 的会话和 Mapper 代理接入 Spring 容器与 Spring 事务。
- `mybatis-spring-boot-autoconfigure`：提供 `MybatisAutoConfiguration` 和 `MybatisProperties`，把 Boot 的 DataSource、配置属性和 MyBatis-Spring 组件连接起来。
- `mybatis-spring-boot-starter`：方便一次性引入上述适配层的依赖集合。

因此 Starter 不是业务代码，也不是所有自动配置逻辑的唯一存放位置。自动配置类主要来自 `mybatis-spring-boot-autoconfigure`。

### 2. `MybatisAutoConfiguration` 创建了什么，以及依赖哪些条件

你列出的条件注解基本正确。可以按职责理解为：

```text
存在 MyBatis / MyBatis-Spring 必需类
  + 存在一个合适的 DataSource
  + MybatisProperties 能绑定 mybatis.* 配置
  + 用户没有提供冲突的基础设施 Bean
  -> 自动创建 SqlSessionFactory
  -> 自动创建 SqlSessionTemplate
```

典型条件包括：

```java
@ConditionalOnClass({SqlSessionFactory.class, SqlSessionFactoryBean.class})
@ConditionalOnSingleCandidate(DataSource.class)
@EnableConfigurationProperties(MybatisProperties.class)
@AutoConfigureAfter(DataSourceAutoConfiguration.class)
```

`@ConditionalOnSingleCandidate(DataSource.class)` 的含义不是“数据库一定能连通”，而是容器中必须能找到唯一的候选 `DataSource`。如果有多个数据源却没有明确主数据源，自动配置可能无法决定使用哪一个。

自动配置通常提供：

- `SqlSessionFactory`：根据 DataSource、Mapper XML 和 MyBatis 配置构建工厂。
- `SqlSessionTemplate`：实现 Spring 管理的 SqlSession 调用入口。
- MyBatis 配置属性绑定：例如 `mapper-locations`、`type-aliases-package` 和 `configuration.*`。

自动配置不会替你生成 `TaskMapper.xml` 中的业务 SQL，也不会自动理解任务和评论的业务关系。

### 3. `@MapperScan` 为什么能注入 Mapper

你的方向正确，但“最终由 MyBatis 生成接口对象”还可以更精确：

```java
@MapperScan("cn.siyes.training.boot.mapper")
```

大致触发链是：

```text
@MapperScan
  -> @Import(MapperScannerRegistrar.class)
  -> MapperScanRegistrar 向 Spring 注册 ClassPathMapperScanner
  -> 扫描指定包中的 Mapper 接口
  -> 为每个接口注册 MapperFactoryBean
  -> MapperFactoryBean 通过 SqlSessionTemplate 创建 Mapper 代理
  -> 代理对象作为 Bean 注入 Service
```

所以：

- 接口本身不能 `new`；
- Spring 容器里注册的是 Mapper 工厂 Bean；
- 你注入到 Service 的实际对象通常是 JDK 动态代理；
- 调用 `taskMapper.findById(id)` 时，代理根据接口全限定名和方法名查找 `MappedStatement`，再委托给 `SqlSessionTemplate` 执行。

`@MapperScan` 的职责是“发现和注册 Mapper”，不是执行 SQL，也不是创建 `SqlSessionFactory`。

### 4. `SqlSessionTemplate` 为什么能让 Mapper 参与 Spring 事务

这是本轮最需要补充的一点。`SqlSessionTemplate` 本身不是事务管理器，它是 MyBatis-Spring 提供的线程安全 SqlSession 代理，负责把 Mapper 调用转交给当前合适的 SqlSession。

当外部调用带有 `@Transactional` 的 Service 代理时：

```text
Service 代理
  -> Spring 事务拦截器开启事务
  -> DataSourceTransactionManager 绑定事务连接
  -> Mapper 代理调用 SqlSessionTemplate
  -> SqlSessionTemplate 获取当前事务绑定的 SqlSession / Connection
  -> 多个 Mapper 操作使用同一个事务连接
  -> 正常返回：事务管理器 commit()
  -> 运行时异常：事务管理器 rollback()
```

你日志中的：

```text
Fetched SqlSession ... from current transaction
Transaction synchronization committing SqlSession
```

正是 Mapper 调用参与 Spring 事务的证据。

而普通查询如果没有进入事务边界，可能出现：

```text
SqlSession ... was not registered for synchronization
JDBC Connection ... will not be managed by Spring
```

这表示当前调用没有活动的 Spring 事务，通常是正常现象，不等于 MyBatis 配置失败。

### 5. `namespace`、`id`、`#{}` 和 `resultMap`

- `namespace`：绑定 Mapper XML 与 Mapper 接口的全限定名。
- `id`：绑定 XML 中的 SQL 语句与接口方法名。
- `#{}`：参数占位语法。MyBatis 会将其解析成 JDBC 的 `?`，并创建参数映射，通过预编译参数绑定值，不能把它简单理解成文本替换。
- `resultMap`：定义查询列到 Java 属性的映射规则，支持列名别名、类型转换、父子对象、`association` 和 `collection` 等复杂结构。

例如：

```text
namespace = cn.siyes.training.boot.mapper.TaskMapper
id        = findById
```

MyBatis 才能定位到：

```text
cn.siyes.training.boot.mapper.TaskMapper.findById
```

`resultMap` 不只是“返回复杂对象”；即使普通对象也可以用它显式指定字段映射，尤其适合数据库下划线字段、JOIN 别名和一对多结构。

### 6. 为什么 SQL 仍然需要自己写，而 Boot 可以自动提供 `SqlSessionFactory`

你的理解方向正确，应该补充职责差异：

- `SqlSessionFactory` 是 MyBatis 的基础设施工厂，负责保存全局配置、Mapper 语句和执行环境，并创建 SqlSession；
- SQL 是具体业务行为，涉及表结构、筛选条件、分页、排序、关联和索引，框架无法替每个项目预先生成正确实现；
- Boot 能根据统一的配置创建工厂，但不会知道“任务详情应该怎样 JOIN 评论”。

因此：

```text
Boot 自动配置基础设施
MyBatis 解析和执行 SQL
开发者设计业务 SQL、参数和结果映射
```

### 7. Repository 适配层能隔离到什么程度

你关于任务 CRUD 的结论基本成立：`Service -> TaskRepository`，由 `MyBatisTaskRepository` 在内部组合 `TaskMapper`，可以让任务 CRUD 的 Service 不直接依赖 MyBatis 具体接口。切换实现时，只要保证容器中最终只有一个 `TaskRepository` 候选，或使用 `@Primary` / `@Qualifier` 明确选择即可。

但结合当前代码，需要修正为：

```java
private final TaskRepository taskRepository;
private final TaskCommentMapper taskCommentMapper;
private final TaskDetailMapper taskDetailMapper;
```

当前 Service 对任务 CRUD 通过 Repository 抽象，对评论批量新增和详情查询仍然直接依赖 MyBatis Mapper。因此不能说“Controller 和 Service 完全不感知 MyBatis”；准确说法是：

- 任务 CRUD 已通过 Repository 适配层隔离；
- 评论和详情仍采用直接 Mapper 注入，是本轮为了减少额外适配代码的训练取舍；
- 如果要彻底隔离，可以再增加 `CommentRepository`、`TaskDetailRepository`，但会引入更多适配层代码。

这两种设计都可以，关键是明确边界和取舍。学习阶段保留当前混合方式，有利于同时观察 Repository 抽象和 Mapper 直接使用。

### 8. `useGeneratedKeys` 如何回写主键

配置：

```xml
<insert id="insert"
        useGeneratedKeys="true"
        keyProperty="id"
        keyColumn="id">
```

过程是：

```text
MyBatis 执行 INSERT
  -> JDBC 驱动返回数据库生成的主键
  -> KeyGenerator 读取主键
  -> 通过 keyProperty 写回传入对象的 id 属性
```

所以调用结束后，传入的 `Task` 对象会从：

```text
id = null
```

变为：

```text
id = 数据库自增值
```

这依赖数据库、JDBC 驱动和属性 setter 都支持生成键回写。`keyProperty` 是 Java 对象属性名，`keyColumn` 是数据库生成键列名，二者不要混淆。

### 9. `<collection>` 如何把 JOIN 多行结果合并成父对象

原来的“根据 LEFT JOIN 左表 id 分级”不够准确。MyBatis 的核心过程是：

```text
JOIN 返回多行
  -> 读取父级 <id>
  -> 相同父 id 复用同一个父对象
  -> 读取子级 <id>
  -> 每个不同子 id 创建一个子对象
  -> 放入父对象的 comments 集合
```

例如同一个任务有三条评论，SQL 可能返回三行，但父级：

```xml
<id property="id" column="task_id"/>
```

让 MyBatis 知道三行属于同一个任务；子级：

```xml
<collection property="comments" ofType="TaskComment">
    <id property="id" column="comment_id"/>
</collection>
```

让 MyBatis 创建三条评论并放入集合。

使用 `LEFT JOIN` 时，没有评论的任务仍然可以查出；评论列为空时，子集合的具体表现受结果映射和 MyBatis 配置影响，业务层应明确约定返回空集合还是 `null`。

### 10. MyBatis Mapper 事务与原生 MyBatis 手动 `commit()` 的区别

原生 MyBatis：

```text
openSession()
  -> mapper 操作
  -> session.commit() 或 session.rollback()
  -> session.close()
```

提交、回滚和会话关闭由开发者手动控制。

Spring Boot + MyBatis：

```text
外部调用 @Transactional Service 代理
  -> Spring 事务管理器控制 Connection
  -> SqlSessionTemplate 协调当前 SqlSession
  -> Mapper 只负责执行映射语句
  -> 方法结束后由 Spring commit / rollback
```

Mapper 本身没有独立的事务边界，也不应该在 Mapper 或 Service 中手动 `openSession()`、`commit()`、`rollback()`。如果手动创建另一套 SqlSession，可能绕开 Spring 当前事务，导致同一个业务方法中的操作无法一起回滚。

默认情况下，Spring 对运行时异常和错误执行回滚；受检异常是否回滚要根据 `rollbackFor` 等配置确认。事务注解仍然受代理边界影响，同类内部 `this.otherMethod()` 可能绕过代理。

## 三、结合当前代码需要注意的点

### 1. 可选 `status` 参数的空值风险

当前 `MyBatisTaskRepository` 中：

```java
return taskMapper.findPage(keyword, status.name(), offset, limit);
```

以及 `count()` 中的 `status.name()`，当查询请求不传 `status` 时可能触发 `NullPointerException`。因为 `status` 在查询条件中本来是可选的，适配层应在传给 Mapper 前保留 `null`，或由 Mapper 接收 `TaskStatus` 并统一转换。

这不影响你截图中带 `status=DONE` 的验证，但属于后续应修正的边界问题。

### 2. 返回更新条数不等于业务成功

`update()`、`updateStatus()` 和 `deleteById()` 返回的 `int` 是数据库实际影响的行数。业务层仍应决定：

- 影响行数为 `0` 是否代表任务不存在；
- 是否先查询再更新；
- 并发更新时是否需要乐观锁或版本号。

当前项目采用“先查询，不存在就抛异常”的训练写法，重点是理解返回行数和业务异常的区别。

### 3. 查询日志的用途和边界

本轮开启 `StdOutImpl` 是为了观察：

- 最终 SQL；
- 绑定参数；
- 返回列和行数；
- SqlSession 是否参与当前事务。

它适合训练，不适合直接作为生产日志方案。生产环境还需要考虑日志级别、敏感参数脱敏、日志格式、采集方式和性能。
