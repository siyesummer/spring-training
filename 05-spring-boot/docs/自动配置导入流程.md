# Spring Boot 自动配置导入流程

本文专门记录 Spring Boot 中 `AutoConfigurationImportSelector` 如何被触发，以及候选自动配置类如何最终变成容器中的 Bean。以当前项目 Spring Boot `4.0.8` 为基线。

## 一、先看完整链路

```text
SpringApplication.run()
  -> 创建 ApplicationContext
  -> refresh()
  -> ConfigurationClassPostProcessor
  -> 解析 @SpringBootApplication
  -> 解析 @EnableAutoConfiguration
  -> 发现 @Import(AutoConfigurationImportSelector.class)
  -> 延迟执行 AutoConfigurationImportSelector
  -> 读取候选自动配置类
  -> 应用排除项和条件筛选
  -> 返回最终配置类名称
  -> Spring 继续解析自动配置类
  -> 注册 BeanDefinition
  -> 创建 Bean 并完成依赖注入
  -> 启动内嵌 Tomcat
```

关键点：`AutoConfigurationImportSelector` 主要负责“选择自动配置类”，不是直接创建所有 Bean。具体 Bean 通常由自动配置类中的 `@Bean` 方法声明，最后仍由 Spring 容器负责注册和实例化。

## 二、`@SpringBootApplication` 如何引入自动配置

`@SpringBootApplication` 是组合注解，可以简化理解为：

```java
@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan
```

`@EnableAutoConfiguration` 的关键元注解是：

```java
@AutoConfigurationPackage
@Import(AutoConfigurationImportSelector.class)
public @interface EnableAutoConfiguration {
}
```

真正把 `AutoConfigurationImportSelector` 放入 Spring 配置解析流程的是：

```java
@Import(AutoConfigurationImportSelector.class)
```

这里的 `@Import` 来自 Spring Framework，不是 Spring Boot 独有的注解。

## 三、Spring 什么时候触发它

应用启动时，Spring 会执行 `ConfigurationClassPostProcessor`。它负责解析配置类中的：

- `@Configuration`；
- `@ComponentScan`；
- `@Import`；
- `@Bean`；
- 条件注解。

当它解析 `Application` 时，发现 `@SpringBootApplication` 元注解中的 `@EnableAutoConfiguration`，继续发现：

```java
@Import(AutoConfigurationImportSelector.class)
```

于是 Spring 创建 `AutoConfigurationImportSelector`，并将它识别为 `DeferredImportSelector`。它不会在发现 `@Import` 的瞬间立即导入全部自动配置，而是先登记，等普通配置类解析完成后统一处理。

这样可以让组件扫描、普通配置和自动配置按明确的阶段处理，也便于自动配置之间进行排序。

## 四、候选自动配置类从哪里读取

延迟导入阶段会调用：

```java
selectImports(AnnotationMetadata metadata)
```

内部可以简化为：

```text
selectImports()
  -> getAutoConfigurationEntry()
  -> getCandidateConfigurations()
```

Spring Boot 4 中，候选读取逻辑可以理解为：

```java
ImportCandidates.load(AutoConfiguration.class, classLoader)
```

它会读取 Boot 约定的资源文件：

```text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

该文件位于 `spring-boot-autoconfigure` 等 Jar 中，通常一行写一个自动配置类的全限定名，例如：

```text
org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
org.springframework.boot.autoconfigure.jdbc.JdbcTemplateAutoConfiguration
org.springframework.boot.autoconfigure.web.servlet.ServletWebServerFactoryAutoConfiguration
```

这不是扫描所有 Java 类，而是通过类加载器查找约定位置的候选清单，并合并多个 Jar 中的内容。

## 五、候选类读取后如何筛选

读取候选类后，不会无条件全部导入，而是经过类似以下流程：

```text
候选自动配置类
  -> 去重
  -> 处理 @EnableAutoConfiguration 的 exclude
  -> AutoConfigurationImportFilter 过滤
  -> 条件判断
  -> 自动配置排序
  -> 返回最终配置类名称
```

常见条件包括：

```java
@ConditionalOnClass
@ConditionalOnMissingBean
@ConditionalOnProperty
@ConditionalOnWebApplication
```

例如，JDBC 相关自动配置需要 classpath 中存在 Spring JDBC 类，并且容器中存在符合条件的 `DataSource`。如果用户已经声明了同类型 Bean，Boot 的默认配置通常会因为 `@ConditionalOnMissingBean` 不满足而退让。

## 六、`selectImports()` 返回什么

`selectImports()` 最终返回的是配置类名称数组：

```java
String[]
```

例如：

```text
org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
org.springframework.boot.autoconfigure.jdbc.JdbcTemplateAutoConfiguration
org.springframework.boot.autoconfigure.web.servlet.DispatcherServletAutoConfiguration
```

这里返回的只是“应该继续解析哪些配置类”，不是 `DataSource`、`JdbcTemplate` 或 `DispatcherServlet` 实例。

## 七、自动配置类如何产生具体 Bean

Spring 收到最终配置类名称后，会把这些类继续当作配置类解析。

例如，解析 `JdbcTemplateAutoConfiguration` 后，可能继续导入 `JdbcTemplateConfiguration`，其中有类似这样的 Bean 方法：

```java
@Bean
JdbcTemplate jdbcTemplate(DataSource dataSource) {
    return new JdbcTemplate(dataSource);
}
```

最终过程是：

```text
自动配置类中的 @Bean 方法
  -> BeanDefinition
  -> BeanDefinitionRegistry
  -> Spring 实例化 JdbcTemplate
  -> 根据构造器完成依赖注入
```

因此职责要分开：

| 环节 | 主要职责 |
| --- | --- |
| `@ComponentScan` | 扫描项目中的组件类 |
| `AutoConfigurationImportSelector` | 读取并选择 Boot 自动配置类 |
| 自动配置类中的 `@Bean` | 声明具体基础设施 Bean |
| Spring 容器 | 注册 BeanDefinition、实例化 Bean、完成依赖注入 |

## 八、当前项目中的实际对应关系

### 1. Web 层

```text
spring-boot-starter-webmvc
  -> MVC 和内嵌 Tomcat 类进入 classpath
  -> Web 自动配置条件满足
  -> ServletWebServerFactoryAutoConfiguration
  -> 启动内嵌 Tomcat
  -> DispatcherServletAutoConfiguration
  -> 注册 DispatcherServlet
  -> Controller 接收请求
```

所以当前项目没有手动注册 `DispatcherServlet`，不是因为它不需要注册，而是这一步由 Boot 自动配置完成。

### 2. JDBC 层

```text
BOOT_DB_* 环境变量
  -> Spring Environment
  -> DataSource 自动配置
  -> 创建 HikariDataSource
  -> JdbcTemplate 自动配置
  -> 创建 JdbcTemplate
  -> TaskRepository 构造器注入 JdbcTemplate
```

`JdbcTemplate` 不是被 `@ComponentScan` 扫描出来的，而是由自动配置类的 `@Bean` 方法注册的。

## 九、与 `@ComponentScan` 的区别

两者都可能最终让 Bean 出现在容器中，但入口不同：

```text
@ComponentScan
  -> 扫描项目 classpath 下指定包
  -> 找到 @Controller / @Service / @Repository / @Component

@EnableAutoConfiguration
  -> @Import(AutoConfigurationImportSelector.class)
  -> 读取 AutoConfiguration.imports
  -> 选择自动配置类
  -> 自动配置类中的 @Bean 注册基础设施
```

普通的 DTO、model 类不会因为位于启动类子包就自动成为 Bean；自动配置类也不是通过普通组件扫描发现的。

## 十、如何观察和验证这条流程

可以在当前项目中做以下观察：

1. 查看启动日志，确认内嵌 Tomcat、Hikari 数据源和 Actuator 都被启动。
2. 在 `TaskRepository` 中保持构造器注入 `JdbcTemplate`，不声明自己的 `JdbcTemplate` Bean。
3. 访问 `/tasks/1`，验证 `Controller -> Service -> JdbcTemplate -> DataSource -> MySQL` 链路。
4. 临时声明一个自己的 `JdbcTemplate` Bean，观察默认 `JdbcTemplate` 自动配置是否因 `@ConditionalOnMissingBean` 退让。验证后恢复代码。
5. 使用 `--debug` 启动参数查看条件评估报告，观察哪些自动配置匹配成功、哪些因条件不满足而未生效：

```powershell
java -jar target\05-spring-boot-0.0.1-SNAPSHOT.jar --debug
```

`--debug` 主要帮助观察条件评估结果，不代表所有自动配置类都已经创建了 Bean。

## 十一、一句话总结

> `@EnableAutoConfiguration` 通过 `@Import` 注册 `AutoConfigurationImportSelector`；Spring 的 `ConfigurationClassPostProcessor` 在解析配置类时延迟调用它；它读取 `AutoConfiguration.imports` 中的候选配置类，经过排除项和条件筛选后返回配置类名称，最后由 Spring 继续解析这些配置类并注册具体 Bean。
