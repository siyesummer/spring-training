## 二、问题修正与机制说明

### 1. Spring Boot 与 Spring Framework 的关系

Spring Framework 提供 IoC 容器、AOP、事务、Spring MVC 等基础能力；Spring Boot 建立在这些能力之上，提供：

- Starter 依赖组合；
- 自动配置；
- 外部化配置和 Profile；
- 内嵌 Web 容器与可执行 Jar；
- Actuator、日志和基础工程化约定。

所以 Boot 不只是“创建项目时使用的脚手架”。脚手架主要帮助生成初始目录和配置，Boot 还会在应用启动时参与环境准备、自动配置、Bean 创建和 Web 容器启动。前端类比可以帮助理解，但不能把 Boot 等同于一次性的脚手架工具。

### 2. `@SpringBootApplication` 由什么组成

它是一个组合注解，核心可以理解为：

```java
@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan
```

- `@SpringBootConfiguration`：表明该类是 Boot 应用的主要配置类，本质上属于 `@Configuration` 的特殊标记。
- `@EnableAutoConfiguration`：通过 `@Import(AutoConfigurationImportSelector.class)` 触发自动配置候选类的选择和导入。
- `@ComponentScan`：从启动类所在包开始向下扫描组件，发现 `@Controller`、`@Service`、`@Repository`、`@Component` 等类后注册为 Bean。它不是扫描并注册所有 Java 类；普通 DTO、model 类不会因为位于子包就自动成为 Bean。

启动类放在 `cn.siyes.training.boot` 根包，是为了让组件扫描覆盖 `controller`、`service`、`repository` 等子包。

### 3. Starter、自动配置类和条件注解的关系

原来的“Starter 里包含自动配置类”不够准确。更准确的链路是：

```text
Starter（依赖集合）
  -> 把相关库放入 classpath
  -> @EnableAutoConfiguration 导入候选自动配置类
  -> 条件注解判断当前环境
  -> 满足条件时注册基础设施 Bean
```

例如，`spring-boot-starter-jdbc` 主要负责引入 Spring JDBC、连接池等依赖；`JdbcTemplateAutoConfiguration` 等自动配置类通常来自 `spring-boot-autoconfigure`，不是 Starter 本身直接保存的业务实现。

常见条件包括：

- `@ConditionalOnClass`：classpath 中存在指定类；
- `@ConditionalOnMissingBean`：用户没有自己提供同类型 Bean；
- `@ConditionalOnProperty`：配置属性满足条件；
- Web 应用类型、Profile 等其他条件。

这体现了 Boot 的设计：提供合理默认值，同时允许用户通过自己的 Bean 或配置覆盖默认行为。

### 4. 自动导入 `AutoConfiguration` 在哪里触发

真正的触发点是 `@EnableAutoConfiguration`：

```java
@Import(AutoConfigurationImportSelector.class)
```

`AutoConfigurationImportSelector` 会读取 Boot 约定的候选清单：

```text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

它收集候选自动配置类，再应用排除项和条件注解进行筛选，最后把符合条件的配置类交给 Spring 配置类解析流程。它不是简单地扫描所有 Jar 中任意名称匹配的 `.imports` 文件，也不是导入后无条件创建全部 Bean。

### 5. 为什么没有手动注册 `DispatcherServlet` 仍能接收请求

在前面的传统 Spring MVC WAR 项目中，你通过 `web.xml` 或初始化配置手动注册了 `DispatcherServlet`。本项目没有手写这一步，是因为 Web Starter 让 MVC 和内嵌 Tomcat 相关类出现在 classpath 中，自动配置条件成立后，`DispatcherServletAutoConfiguration` 注册了 `DispatcherServlet` 及其相关 MVC 基础设施。

启动链可以简化为：

```text
SpringApplication.run()
  -> 自动配置 Web 环境
  -> 启动内嵌 Tomcat
  -> 注册 DispatcherServlet
  -> DispatcherServlet 接收请求并交给 Controller
```

因此这里是“没有手动注册”，不是“手动注册后又被自动配置了一次”。

### 6. 为什么没有手动声明 `JdbcTemplate` 仍然可以注入

`spring-boot-starter-jdbc` 使 Spring JDBC 和连接池依赖可用；当数据源属性存在并且容器中没有用户自定义 `DataSource` 时，Boot 会先自动配置 `DataSource`。随后 `JdbcTemplateAutoConfiguration` 在存在 `DataSource` 且没有用户自定义 `JdbcOperations` 时注册 `JdbcTemplate`。

可以把本项目的链路理解为：

```text
BOOT_DB_* 环境变量
  -> Spring Environment
  -> DataSource 自动配置
  -> JdbcTemplate 自动配置
  -> 构造器注入 JdbcTemplate
```

`JdbcTemplate` 并不是因为实现类被组件扫描发现，而是自动配置类中的 `@Bean` 方法注册到容器中。

### 7. 自定义 `DataSource` 或 `JdbcTemplate` 后会怎样

`@ConditionalOnMissingBean` 的含义是“只有容器中没有用户 Bean 时才使用默认配置”。

- 如果自己声明 `DataSource`，Boot 默认创建连接池数据源的配置会退让；但基于这个 `DataSource` 的 `JdbcTemplate` 和事务管理器仍可能继续自动配置。
- 如果自己声明 `JdbcTemplate` 或其他 `JdbcOperations`，Boot 默认的 `JdbcTemplate` Bean 会退让。

所以不能简单说“DataSource 自动配置失效后，所有相关自动配置都失效”。准确说法是：被覆盖的那一段默认配置不再创建，其他满足条件的自动配置仍可基于用户 Bean 继续工作。

### 8. `application.yaml`、环境变量和 Profile

本项目的配置关系是：

```text
application.yaml
  + application-dev.yaml（激活 dev 后覆盖同名属性）
  + 环境变量 BOOT_DB_*（填充数据源敏感值）
  -> Spring Environment
  -> DataSource / Web Server / Actuator 配置
```

Profile 文件通常是在基础配置之上覆盖或补充属性，而不是把基础文件整个替换掉。本项目中 `application-dev.yaml` 将端口从 `8085` 覆盖为 `8086`，截图和启动日志已经证明 `dev` Profile 生效。

需要区分两件事：配置文件负责声明属性来源，自动配置类负责读取这些属性并创建对象。环境变量不会自动修改数据库，它只是被 Java 进程读取的运行时配置。

### 9. 为什么使用 Jar 和内嵌 Tomcat

本项目使用 Web Starter，运行时带有内嵌 Tomcat。`SpringApplication.run()` 创建 Web 应用上下文并启动该 Tomcat，因此不需要单独安装外部 Tomcat，也不需要先部署 WAR。

前面的项目使用 WAR，是因为应用把 Servlet 组件交给外部 Tomcat 承载；当前项目把应用和容器一起打包，启动入口由 Jar 自己提供。

### 10. `java -jar` 的 Jar 与普通 Maven Jar

普通 Maven Jar 通常只包含项目自己的 `.class` 和资源文件，依赖仍需要通过外部 classpath 提供。

Spring Boot Maven 插件会把项目重新打包成可执行 Jar，典型结构包括：

```text
BOOT-INF/classes/   项目自己的 class 和资源
BOOT-INF/lib/       运行时依赖 Jar
org/springframework/boot/loader/  Boot Loader
META-INF/MANIFEST.MF 启动入口信息
```

执行：

```powershell
java -jar target\05-spring-boot-0.0.1-SNAPSHOT.jar
```

由 Boot Loader 组装运行时 classpath，再调用应用的 `main()`，最终启动内嵌 Tomcat。`*.jar.original` 是重打包前保留的普通 Jar，主要用于对照，不是本项目的完整运行产物。

### 11. `@Transactional` 与代理边界

`@Transactional` 不是把每一条 SQL 自动变成“立即提交”。它由 Spring 事务拦截器通过代理包围目标方法：

1. 外部调用代理对象的方法时，事务拦截器开启或加入事务。
2. 方法正常返回时提交事务。
3. 默认情况下，运行时异常或错误导致回滚；受检异常默认不一定回滚，需要按需要配置 `rollbackFor`。
4. 方法执行结束后释放事务资源。

和 Spring Core 阶段一样，同一个类内部的 `this.otherMethod()` 是直接调用目标对象，绕过代理，因此不会单独触发 `otherMethod()` 上的事务拦截。事务边界应该放在能够被外部代理调用的 Service 方法上。

### 12. 如何判断 `linux-server` 中哪些是 Boot 自动配置

可以按三个问题判断：

1. 这个 Bean 是否由项目源码中的 `@Component`、`@Service`、`@Repository`、`@Configuration` 或 `@Bean` 明确声明？如果是，通常属于项目自己的配置或业务代码。
2. 这个 Bean 是否来自 Starter 对应的自动配置类，且创建条件依赖 classpath、属性或 `@ConditionalOnMissingBean`？如果是，通常属于 Boot 自动配置结果。
3. 这个配置是否只是把环境变量绑定到项目自己的配置对象，例如 `@ConfigurationProperties`？绑定机制由 Boot 提供，但配置类和业务含义属于项目自身。

例如，`DispatcherServlet`、默认 `DataSource`、`JdbcTemplate` 和 Actuator 端点通常是 Boot 自动配置结果；Controller、Service、Repository、DTO、业务异常和 SQL 则是项目自己的代码。阅读时可以从 Bean 的声明位置、启动日志、条件注解和依赖来源交叉确认，不要仅凭类名猜测。
